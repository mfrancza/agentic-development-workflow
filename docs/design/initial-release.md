# Design: Initial v1.0.0 release

**Issue:** [#451](https://github.com/mfrancza/agentic-development-workflow/issues/451)

## Summary

Ship the first supported release of this repo so the adoption path documented
in [`docs/adopting.md`](../adopting.md) — pinning workflows at `@v1`,
Terraform modules at `?ref=v1`, and container images at `:v1` — actually
resolves against real published artifacts. Today the repository has zero git
tags, zero GitHub Releases, and no images pushed to GHCR, so every step of
the adoption guide fails at its first prerequisite (verified 2026-09-07 in
issue #451).

The release tooling that this design activates was already delivered by the
publish-reusable-workflows work under issue
[#256](https://github.com/mfrancza/agentic-development-workflow/issues/256):

- [`.github/workflows/release.yml`](../../.github/workflows/release.yml) —
  manual `workflow_dispatch` that validates a `v<M>.<m>.<p>` input, creates
  the annotated version tag, force-updates the moving `v<M>` tag, and
  publishes a GitHub Release with autogenerated notes.
- [`.github/workflows/release-images.yml`](../../.github/workflows/release-images.yml)
  — fires automatically on any `v*` tag push and builds/pushes both agent
  images to GHCR as `:v<M>.<m>.<p>` and moving `:v<M>` tags.

Nothing in this design changes those workflows or writes new release code.
The work is the human-gated ceremony of confirming main is release-ready,
dispatching `release.yml` with `version=v1.0.0`, verifying the images
publish and become publicly pullable, running the adoption guide end-to-end
from an external repo, and folding any discovered gotchas back into
`docs/adopting.md`.

## Requirements as understood

From issue #451, its grooming Q&A, and the existing publish design
([`docs/design/publish-reusable-workflows-and-modules.md`](publish-reusable-workflows-and-modules.md)):

1. **A versioned release tag and moving major tag must exist.** `v1.0.0`
   (exact) and `v1` (moving major) on origin, both pointing at the same
   commit — the semver contract locked in by publish design Decision 6.
2. **Both agent container images must be published to GHCR with the
   documented tags** — `developer:v1.0.0`, `developer:v1`, `reviewer:v1.0.0`,
   `reviewer:v1` — and must be publicly pullable from a repository outside
   this account (no `docker login` required).
3. **A GitHub Release must exist** for `v1.0.0` with autogenerated notes,
   marked `latest`. This matches what `release.yml` already produces.
4. **The adoption path in `docs/adopting.md` must be end-to-end verified**
   from an external repo (the reporting issue names `mfrancza/drone-laser-tag`
   as the intended tester) against the just-published `v1` artifacts, and
   any gotchas discovered must be folded back into the adoption guide before
   this issue is closed.
5. **A human owns the release decision.** Publishing v1.0.0 is
   consequential and largely irreversible (releases and tags can be deleted
   but the artifacts remain in downloaders' caches and dependency graphs); a
   human must confirm the codebase is releasable and dispatch the workflow.

The parent issue #451 already carries `human-required` and is assigned to
@mfrancza; sub-issues covering the human-only steps inherit both.

### Ambiguity resolutions

- **Primary path vs. fallback path.** The issue offers two branches:
  either publish v1.0.0, or mark release-based adoption unavailable and
  document a source-commit installation instead. This design plans **only
  the primary path**. Rationale: the release tooling already exists and is
  tested-shaped (issues [#403](https://github.com/mfrancza/agentic-development-workflow/issues/403)
  and [#400](https://github.com/mfrancza/agentic-development-workflow/issues/400)
  landed the two workflows), the adoption guide is already written against
  `@v1`, and every design task under issue #256 that produced the `v1`
  surface has merged. If the readiness audit (Task 1) surfaces a blocker
  that must be fixed before releasing, the fallback becomes a separate
  design under a new issue — not a pre-planned branch here. Documenting
  both paths as sub-issues would imply the fallback is scheduled work; it
  is not, unless Task 1 flips the outcome.
- **How to create the tags.** The issue's grooming notes suggest
  `git tag v1.0.0 && git tag -f v1` as a fallback command. This design uses
  `release.yml` instead: it validates the version format, checks for tag
  collisions, tags at the checked-out SHA of `main`, force-updates the
  moving `v1`, pushes both, and creates the GitHub Release with generated
  notes — all as one auditable workflow run. Direct `git push --tags` would
  skip the Release creation and bypass the audit trail this repo's release
  contract expects.
- **Who runs the external smoke test.** Task 4 (adoption smoke test) is
  scoped as a human task, not an agent task. Executing the adoption guide
  end-to-end requires installing two GitHub Apps on the target repo,
  provisioning secrets, running `terraform apply` from a local machine, and
  observing a live grooming run — cross-repo credentials that the design
  and developer agents in this repo deliberately do not have (least-privilege
  posture in AGENTS.md § Key Design Constraints).
- **Image visibility.** GHCR packages pushed from a public repo are
  publicly readable by default, but the package's visibility can be
  overridden in Package settings independently of the source repo's
  visibility. Task 3 (image verification) treats public accessibility as
  something to **verify from outside the account**, not something to
  assume. If the first push lands the packages as private, the fix
  (flipping visibility in the Packages UI or via `PATCH
  /user/packages/container/<name>/visibility`) is captured in the same
  sub-issue and documented as a permanent gotcha in `docs/adopting.md`.

## Decisions

### Decision 1 — Cut v1.0.0 via `release.yml`, not `git push --tags`

**Decision.** The tags and GitHub Release are created by dispatching the
existing `release.yml` workflow with `version=v1.0.0` and `ref=main`. No
maintainer-side `git tag && git push` is used.

**Rationale.** `release.yml` already implements the full ceremony this repo
committed to in publish Decision 6: version-format validation, tag-collision
check, annotated tag at the workflow's checked-out SHA, force-updated moving
`v1`, pushed atomically, and a `latest`-marked GitHub Release with
generated notes. The push of `v1.0.0` chains automatically into
`release-images.yml`. A manual `git push` path would skip Release creation,
bypass the validation and collision guards, and produce no workflow-run
audit trail — regressions the design that shipped `release.yml` explicitly
paid for.

**Alternatives considered.**

- **Manual `git tag v1.0.0 && git push --tags origin`.** Rejected for the
  reasons above; noted in the issue grooming Q&A only as a hypothetical
  fallback.
- **Cut a pre-release tag (`v1.0.0-rc.1`) first and promote later.**
  Rejected: adds ceremony without addressing the reporter's blocker. The
  adoption guide is written against `v1`, not `v1-rc`, and the moving `v1`
  tag would still need to be created eventually.

### Decision 2 — Independent readiness audit before dispatch

**Decision.** Task 1 (release readiness audit) runs as a distinct sub-issue
whose sole output is a comment on issue #451 summarizing whether main is
release-ready. Task 2 (the actual dispatch) is gated on the human reading
that report and deciding to proceed.

**Rationale.** The grooming notes call out a "gate check" as step 1 of the
suggested implementation path. Separating audit from dispatch:

- Gives the human a concrete artifact to review before making the
  irreversible decision.
- Lets an agent do the mechanical audit work (query CI status on main, list
  open blocking issues, check for outstanding release-relevant PRs)
  without having any authority to publish.
- Keeps the audit re-runnable: if the human defers dispatch and other work
  lands on main, re-running the audit sub-issue produces a fresh snapshot
  without re-litigating the design.

**Alternatives considered.**

- **Fold the audit into the dispatch task.** Rejected: bundles agent-doable
  work with human-only work; the human would then have to redo the audit
  themselves to be sure. Separation lets the audit lean on an agent for
  toil.
- **Skip the audit and dispatch immediately.** Rejected: the "consequential
  and largely irreversible" nature of a v1.0.0 publish is exactly why
  `human-required` is on the parent. A written go/no-go is the minimum bar.

### Decision 3 — Image publication verified from outside the account

**Decision.** Task 3 (image verification) verifies each of the four
expected tags (`developer:v1.0.0`, `developer:v1`, `reviewer:v1.0.0`,
`reviewer:v1`) is (a) present in GHCR and (b) pullable **without
authentication** — i.e., the packages are actually public. The verification
runs the `docker pull` from a context that has no credentials for
`ghcr.io/mfrancza/*`.

**Rationale.** Publish design Decision 4's "GHCR is public for public
packages by default" is true at *initial* publish, but GHCR container-package
visibility is an independent Packages-page setting that can drift silently
(e.g., if a maintainer flips it in the UI). The adoption guide already
documents this class of failure ("GHCR image pull fails in workflow"
gotcha), so verifying it at initial release is the single point at which we
can catch a misconfiguration before external adopters do.

**Alternatives considered.**

- **Trust that the packages published as public and skip verification.**
  Rejected: the gotcha exists in the adoption guide precisely because this
  assumption has failed for other users; verifying once at initial release
  is cheap insurance.
- **Verify only that images exist (via `gh api /user/packages/...`), not
  that they pull without auth.** Rejected: the failure mode is pullability,
  not existence. A private package is still "present" but breaks every
  consumer.

### Decision 4 — External smoke test from a real consumer repo

**Decision.** Task 4 (adoption smoke test) is executed manually by a human
against a real external repository — the reporter names
`mfrancza/drone-laser-tag`. The task walks the `docs/adopting.md`
quick-start end-to-end against the just-published `v1` artifacts and closes
only when at least one agent (the grooming agent is the smallest useful
target) has successfully run against the consumer repo using the pinned
`ghcr.io/mfrancza/…/developer:v1` image.

**Rationale.** The unit at which this issue's blocker resolves is "the
adoption guide's first prerequisite passes for an external repo," so the
verification must happen from an external repo. Two design precedents
apply:

- The publish-reusable design already scoped its final task (Issue
  [#407](https://github.com/mfrancza/agentic-development-workflow/issues/407))
  as an end-to-end validation from a scratch consumer repo. This design
  intentionally does the same thing at the very next release event, treating
  the first release-cut as one more validation point.
- Automation for this validation is explicitly listed as future work in
  publish design "Out of scope" — a continuous cross-repo CI loop is not
  built here either.

**Alternatives considered.**

- **Have the agent run a synthetic verification (e.g., `docker pull` + a
  `gh workflow view` against a `@v1` ref).** Rejected: catches image and
  workflow-ref availability but not the many-variable-per-consumer surface
  the adoption guide covers (Terraform apply, App installation, secrets).
  A synthetic check is already implicit in Task 3.
- **Validate against a fresh throwaway repo the design agent creates.**
  Rejected: cross-repo credentials required (App installation is
  interactive; secrets need to be set out of band). Not agent-authorable.

### Decision 5 — Adoption-guide amendments come after the smoke test

**Decision.** Task 5 (adoption-guide update) depends on Task 4 finishing.
The amendment updates the "Images and workflow refs not found" gotcha to
reference the concrete `v1.0.0` release, adds a "Verified against" line to
the quick-start referencing this issue, and folds in whatever new gotchas
Task 4 surfaced.

**Rationale.** Updating the guide before the smoke test would either
duplicate the guide's forward-looking language (it already promises `@v1`
will work) or hard-code assumptions that the smoke test then invalidates.
The right time to promise "v1.0.0 was verified end-to-end" is right after
the verification actually happened.

**Alternatives considered.**

- **Skip the docs update; rely on the release notes for user-facing
  signal.** Rejected: the specific gotcha this issue instantiates ("no
  release exists yet") lives in `docs/adopting.md`, not the release notes.
  Leaving that unchanged when the state has actually flipped is exactly
  the doc-drift AGENTS.md § Keeping Documentation Current tries to prevent.
- **Rewrite the guide's `@v1` references to `@v1.0.0`.** Rejected: the
  moving `v1` tag is the design's recommended pin (publish Decision 6);
  pinning docs to `@v1.0.0` would drop that recommendation on the floor.

## Out of scope

- **The fallback "release-based adoption unavailable, document
  source-commit path" branch of issue #451.** Only invoked if the readiness
  audit surfaces a blocker; if it does, a new issue is opened and this
  design does not pre-plan the sub-issues for it.
- **Cutting subsequent releases (v1.0.1, v1.1.0, v2.0.0).** The cadence
  and criteria for post-v1.0.0 releases is separate design work; this
  design only covers the initial cut.
- **Automating a cross-repo v1 validation on every release.** Explicitly
  future work in the publish-reusable design; the smoke test here is a
  one-time human validation.
- **Image signing / provenance attestation
  (`actions/attest-build-provenance`).** Explicitly future work in publish
  Decision 4; adding it does not gate v1.0.0.
- **Reusable-workflow portability issues discovered during external
  testing** — the issue reporter explicitly scopes these to a separate
  follow-up issue.
- **Any change to `release.yml` or `release-images.yml`.** If Task 1
  reveals either workflow is not release-ready, the fix goes through the
  normal issue → design → implement flow, not this design.
- **Setting up branch protection, Actions policy, or interaction limits on
  the external smoke-test repo.** The adoption guide already tells adopters
  how to do this manually; the smoke test follows the guide.

Tasks are strictly serial: Task 1 → Task 2 → Task 3 → Task 4 → Task 5.
Every downstream step depends on the previous step's real-world artifact
(the audit report, the pushed tags, the pullable images, the smoke-test
findings) — no parallelization is safe here.

Tasks 2 and 4 carry `human-required` and are assigned to @mfrancza because
they cannot be done by an agent (Task 2 owns the release-decision gate;
Task 4 requires cross-repo credentials the agents do not have). Tasks 1,
3, and 5 are agent-authorable and carry `draft` + `enhancement` per the
normal designer-agent sub-issue convention.
