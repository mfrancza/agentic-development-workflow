# Design: Opt-in conflict resolution for non-agent-authored PRs

**Issue:** [#802](https://github.com/mfrancza/agentic-development-workflow/issues/802)

**Parent designs:**
- [`docs/design/resolve-conflicts.md`](resolve-conflicts.md) (Issue #54) — the overall feature contract
- [`docs/design/agent-resolve-conflicts-workflow.md`](agent-resolve-conflicts-workflow.md) (Issue #64) — the push-triggered workflow
- [`docs/design/resolve-conflicts-developer-author.md`](resolve-conflicts-developer-author.md) (Issue #580) — the configurable developer-author contract

## Summary

Today `agent-resolve-conflicts` only touches PRs authored by one developer-agent App login — the parent design explicitly leaves "conflicts on human-authored PRs" out of scope and the finder's GitHub search query carries a mandatory `author:<developer-author>` qualifier. This design adds two opt-in mechanisms so operators can extend the resolver beyond agent-authored PRs without breaking the current default:

1. A repository-level author allowlist (`RESOLVE_CONFLICTS_AUTHOR_ALLOWLIST`, default `[]`) that extends the push-to-`main` enumeration beyond the developer-agent to specific trusted authors or to every open PR (via the `["*"]` wildcard).
2. A per-PR label trigger (`agent:resolve-conflicts`) that an allowlisted operator can apply to any single PR to run the resolver against it on demand, regardless of the repo-wide setting or the PR's author.

Both mechanisms funnel into the existing `agent-resolve-conflicts-reusable.yml` reusable workflow (which already supports a `pr-number` passthrough that bypasses the authorship filter — the `workflow_dispatch` operator-override path). The default behavior is unchanged: a fresh repo sees exactly the agent-only enumeration it sees today.

## Requirements as understood

From Issue #802 and its single grooming comment:

1. **Scope setting** — "Add a setting for running it automatically on all PRs vs just agent-created ones." A repository-wide, Terraform-managed configurable author list that extends the push-to-`main` enumeration from "developer-agent-authored only" (today's behavior, the default) to specific trusted authors or all open PRs. The default must preserve the current behavior.
2. **On-demand label trigger** — "as well as a label that can be applied to trigger it on demand." A `agent:*`-style label that an allowlisted operator can apply to a specific PR to invoke the resolver immediately on that PR, independent of the enumeration setting and independent of the PR's author.
3. **Grooming context** — the grooming note says these are "architectural changes to the merge conflict resolution system… [that] span multiple components and require design planning before implementation." That is the signal to expose each knob through the full chain (Terraform → Actions variable / label → caller stub → reusable workflow → composite action → TypeScript finder) rather than hardcoding behavior in any one layer.

### Ambiguity resolutions

The issue body is deliberately terse; the following judgment calls are not answered by grooming and are resolved below. They are called out so the reviewer knows which pieces are design-time choices rather than restated requirements.

- **Scope setting name and shape** — a list-of-strings Terraform variable `resolve_conflicts_author_allowlist` surfaced as the JSON-array Actions variable `RESOLVE_CONFLICTS_AUTHOR_ALLOWLIST`. An empty array preserves the current agent-only behavior; `["*"]` sweeps all authors; an explicit list covers the developer-agent plus the named logins. See Decision 1.
- **Label name** — `agent:resolve-conflicts`. Every existing agent-trigger label uses `agent:<action>` where `<action>` names an `AGENT_ACTION` dispatcher case. `resolve-conflicts` is already the entrypoint's action name, so `agent:resolve-conflicts` is the natural extension. See Decision 2.
- **Label-trigger authorization** — gated on `AGENT_ALLOWLIST` sender, following the same pattern as every other user-triggered label workflow. The label itself is not a security boundary; the sender identity is.
- **Fork-headed PRs** — excluded from both the all-authors enumeration and the label-trigger path. The resolver needs to push the merge commit to the PR's head branch, and the developer-agent App installation on the base repo cannot push to a fork. Including fork PRs would guarantee runtime failure after a wasted token mint and container boot. See Decision 5.
- **`conflicts-escalated` label on the label-trigger path** — the reusable removes `conflicts-escalated` after authorization, treating the `agent:resolve-conflicts` application as an explicit operator re-attempt. This ensures an unauthorized sender cannot clear the escalation marker. See Decision 4.
- **Label lifecycle after a successful run** — the reusable removes `agent:resolve-conflicts` on success and leaves it in place on failure, matching the `agent:groom` convention described in `AGENTS.md § Labels`. All label mutations happen after the sender has been authorized.
- **Humans opting out of the extended sweep** — out of scope; see "Out of scope" below. Operators who want to include only specific trusted humans use the explicit-list form of `RESOLVE_CONFLICTS_AUTHOR_ALLOWLIST` rather than `["*"]`, which naturally excludes untrusted contributors. For individual PR opt-outs, the escape hatch is to apply `conflicts-escalated` to pin that PR out of the sweep.

## Decisions

### Decision 1 — A configurable author allowlist, not a simple boolean

**Decision.** Add a new list-of-strings Terraform variable `resolve_conflicts_author_allowlist` (type `list(string)`, default `[]`) and expose it as a repository Actions variable `RESOLVE_CONFLICTS_AUTHOR_ALLOWLIST` whose value is a JSON array of GitHub login strings (e.g., `["alice", "bob"]`) or the special wildcard `["*"]`. The variable governs which PR authors the push-to-`main` enumeration sweep covers:

- **`[]` (empty, default)** — the finder uses `author:<developer-author>` and sweeps only developer-agent-authored PRs. Current behavior is fully preserved.
- **`["*"]` (wildcard)** — the finder drops the `author:` qualifier entirely and enumerates every open PR using the REST Pulls API (`GET /repos/{owner}/{repo}/pulls?state=open&per_page=100`) rather than the GitHub Search API, paginating until an empty page is returned, subject to two independent hard stops: a **50-page scan budget** on the enumeration phase and a **100-candidate hard cap** on the filtered (post-fork-filter) candidate set. The 30-req/min rate-limit guard applies to **all** REST requests in the job — each page fetch counts as one request against the same budget as mergeability-poll requests — so a repository with a poor in-scope ratio (many fork PRs or, for the explicit-list mode, many non-allowlisted authors) cannot issue unchecked enumeration bursts that exceed the secondary-rate-limit budget or consume the job's wall-time budget before polling begins. The rate-limit guard is applied before each page fetch and before each polling-attempt wave. When the 50-page scan budget is exhausted before 100 in-scope candidates are collected, the finder emits a `::warning::` annotation — "conflict sweep scan budget exhausted after 50 pages; only N in-scope candidates found; additional in-scope PRs may not have been evaluated — reduce open PR count or use an explicit author allowlist to limit scope" — and stops paginating with the candidates collected so far. When the 100-candidate cap is reached before the page budget is exhausted, the finder emits a `::warning::` annotation — "conflict sweep capped at 100 candidates; additional in-scope PRs may not have been evaluated — reduce open PR count or use an explicit author allowlist to limit scope" — and stops paginating. Unlike the Search API (which silently truncates at 1,000 results), the REST Pulls API has no server-side ceiling; the 50-page scan budget and 100-candidate cap together bound the enumeration scan. Mergeability is polled with **bounded concurrency: P=5 candidates polled simultaneously per batch** (the finder polls a batch of up to 5 candidates in parallel, waits for all to resolve or time out, then moves to the next batch). The rate-limit guard uses **atomic batch reservation**: before each page fetch it waits until `requests_in_last_60s + 1 ≤ 30` and then increments the counter by 1; before each polling-attempt wave it waits until `requests_in_last_60s + batch.length ≤ 30` and then increments the counter by `batch.length` — so the full slot count for the wave is reserved before any parallel request is issued and no wave can burst past the 30-request limit. Both phases share a single rolling 60-second request counter. With `DEFAULT_DELAYS` giving retry attempts at t=0, t+5s, t+15s, t+35s, and t+75s within a batch, the worst-case rolling 60-second window spans the boundary between two consecutive back-to-back batches: it captures wave 5 of batch B-1 (at t+75s from B-1's start) and the first four waves of batch B (at t, t+5s, t+15s, t+35s from B's start), giving 5P = 5×5 = 25 requests in 60 seconds — safely within the 30-req/min secondary-rate-limit budget and without requiring any inter-batch cooldown or per-wave throttling. Because 5P=25 < 30 at every batch boundary, the guard never stalls the steady-state polling phase. At the enum-to-polling transition the guard may add a brief wait (≤ ~10s worst-case) while the last few page-fetch requests age out of the 60-second window before the first polling wave fires: for example, with 28 recent page fetches in the window, the guard waits until at least 3 age out (so that 28 − 3 + 5 = 30 ≤ 30) before atomically reserving the 5-slot batch and launching the first polling wave. The combined worst-case wall time is: enumeration (50 page fetches at ≤30-req/min ≈ 100s) + transition (≤10s) + polling (`ceil(100/5) × 75s = 20 × 75s = 1,500s`) ≈ 1,610s (≈ 26.8 minutes), within the `find-conflicted-prs` job's `timeout-minutes: 30`. This replaces the old `all-authors=true` boolean and uses an enumeration API not subject to a server-side result-count ceiling.
- **Explicit list (e.g., `["alice", "bob"]`)** — the finder drops the `author:` qualifier (the GitHub Search API does not support `author:a OR author:b` natively) and enumerates candidates using the REST Pulls API with the same pagination, 50-page scan budget, 100-candidate hard-cap, global rate-limit guard, and P=5 bounded-concurrency poll strategy as `["*"]`, then applies a post-query author filter that retains only PRs whose author login appears in the set `{<developer-author-bot-login>} ∪ {listed logins}`. **Bot-login normalization:** the GitHub REST Pulls API records a GitHub App's PR authorship as `<app-slug>[bot]` (e.g., `mfrancza-developer-agent[bot]`), but the existing `author` input (env var `INPUT_AUTHOR`) carries the value in `app/<slug>` form (e.g., `app/mfrancza-developer-agent`), not `<slug>[bot]` form. Appending `[bot]` to the raw `author` value yields `app/<slug>[bot]`, which does not match the REST API's `user.login` field. The finder must derive the developer-agent's REST-API bot login by **stripping the `app/` prefix** from the `author` input value and **then** appending `[bot]` (i.e., `${author.replace(/^app\//, '')}[bot]`; example: `app/mfrancza-developer-agent` → strip prefix → `mfrancza-developer-agent` → append suffix → `mfrancza-developer-agent[bot]`). That derived login is included in the matching set so the developer-agent's own PRs are retained rather than excluded. Human logins in the explicit list carry no suffix and are compared verbatim against the REST API `user.login` field. This two-step transformation must be covered by a unit test that asserts a PR whose `user.login` is `<slug>[bot]` is retained when the `author` input is `app/<slug>` (proving that the prefix-strip-then-append transformation is correct and that neither the raw `app/<slug>` form nor the naïve `app/<slug>[bot]` form is compared against the REST API field). The hard cap and warning are applied to the post-filter set so that filtered-out PRs do not consume cap budget. This keeps the developer-agent-authored PRs in scope while extending coverage to specific trusted humans.

The caller stub reads `vars.RESOLVE_CONFLICTS_AUTHOR_ALLOWLIST` and passes it through to the reusable workflow as an `author-allowlist` string input; the reusable passes it through to the `find-conflicted-prs` composite action as the `author-allowlist` input; the composite action passes it to the TypeScript finder as `INPUT_AUTHOR_ALLOWLIST`. The finder parses the JSON, selects the query strategy above, and applies a post-query author filter for the explicit-list case.

**Alternatives considered.**

- **Add a new key to `AUTO_TRIGGER_AGENTS`.** Rejected. That variable's semantics are "which upstream SDLC events auto-apply the next `agent:*` label." The scope of the resolver's enumeration is a different concept, and overloading a single JSON object forces every caller to pre-exist the object in Terraform. The existing single-value precedents (`ENABLE_PROTECTED_APPROVAL_GATE`, `FIX_CHECKS_ALLOW`) are a closer fit.
- **Make it a per-PR label instead of a repo variable.** Rejected because the issue explicitly asks for a *setting* in addition to the on-demand label. Operators who want the sweep for every conflict must not have to label every PR manually. The two mechanisms address different workflows (ambient automation vs. targeted intervention) and both are in scope.
- **Keep a simple boolean (`RESOLVE_CONFLICTS_ALL_AUTHORS`).** Rejected because a boolean cannot express "developer-agent plus specific trusted humans" — the only options are "agent only" or "everyone." A configurable list gives operators the middle-ground they need to avoid running the resolver against PRs from untrusted external contributors, while still enabling the all-authors sweep for repositories that want it.
- **Add a third-state `author-regex`.** Rejected as overfitting. A JSON list of explicit logins (with `["*"]` as the wildcard) covers the requirement clearly and matches the existing `AGENT_ALLOWLIST` list-of-logins convention.

### Decision 2 — `agent:resolve-conflicts` label, modeled on `agent:review`

**Decision.** Add a new repository label `agent:resolve-conflicts` to `terraform/modules/labels/main.tf` with the same `#6f42c1` color used for the other `agent:*` trigger labels, description "Run the merge-conflict resolver against this PR on demand." A new caller stub (or a new trigger on the existing `agent-resolve-conflicts.yml`; see Decision 6) listens for `issues.labeled` where the label name matches (using `issues.labeled` rather than `pull_request.labeled` because GitHub suppresses `pull_request` workflow runs for conflicted PRs — see Decision 6), gates on `vars.AGENT_ALLOWLIST` for the sender, and invokes the existing reusable workflow with `pr-number: ${{ github.event.issue.number }}`.

The reusable's existing `pr-number` input already bypasses the finder's author filter (the `workflow_dispatch` operator-override path from `docs/design/agent-resolve-conflicts-workflow.md` Decision 5), so no finder change is needed to support this trigger — the label-trigger reuses the dispatch-style path.

**Alternatives considered.**

- **`resolve-conflicts` with no `agent:` prefix.** Rejected because every existing agent-dispatch label uses the `agent:<action>` form, and the Labels section of `AGENTS.md` describes the prefix as the trigger-label convention.
- **Overload `agent:developer` to mean "run the resolver on this PR."** Rejected. `agent:developer` triggers `AGENT_ACTION=implement` on issues and would require an issue-vs-PR event conditional. The two actions have distinct entrypoints, distinct tokens-of-work (issue vs. PR), and distinct lifecycle expectations.
- **Use `conflicts-resolve` or `fix-conflicts` as the label name.** Rejected to preserve the pattern recognition value of the `agent:<action>` prefix; a greppable, uniform prefix is easier for operators to filter and for grooming to reason about.

### Decision 3 — Allowlist gating moves into the reusable workflow

**Decision.** The reusable workflow (`agent-resolve-conflicts-reusable.yml`) grows a conditional allowlist-gate job that invokes `./.github/actions/check-agent-allowlist` when a new optional `sender-login` input is non-empty. The push-triggered and `workflow_dispatch`-triggered callers do not pass `sender-login`, so the gate's `skip-gate: 'true'` fires and the existing behavior is unchanged. The label-triggered caller passes `sender-login: ${{ github.event.sender.login }}`, so the gate runs normally and fails closed if the sender is not in `AGENT_ALLOWLIST`.

To support allowlist entries that are `org/team-slug` references, the reusable also declares optional `ALLOWLIST_RESOLVER_APP_ID` / `ALLOWLIST_RESOLVER_APP_PRIVATE_KEY` secrets (both `required: false`), consistent with the other user-triggered reusables. When neither is supplied, team references in the allowlist are skipped with a warning (the existing resolver behavior); login-only allowlists work without configuring the resolver App.

**Alternatives considered.**

- **Gate in the caller stub's `if:` expression.** Rejected per the `AGENTS.md § Repo-specific security defaults` guidance: "Keep caller stubs limited to queue predicates…; reusable preflight gate jobs own lifecycle predicates." Putting the gate in the reusable also means external consumers inherit the gate automatically.
- **Add a separate reusable for the label-trigger.** Rejected as duplicative — the resolve matrix, token minting, and per-PR concurrency group are identical whatever the trigger. A conditional gate is simpler than two parallel reusables that would drift.
- **Always run the gate unconditionally.** Rejected because the push-to-`main` trigger has no human sender (the sender is whoever pushed to `main`, who already needs write access to `main` which is gated by branch protection and the protected-approval gate). Gating it would add a resolver round-trip for no additional authorization value.

### Decision 4 — Label-trigger pre-flights: caller owns read-only queue predicates; mutations follow authorization in the reusable

**Decision.** The label-trigger caller stub (`agent-resolve-conflicts-labeled.yml`) contains only read-only queue predicates and performs no mutations:

- **PR-type queue predicate** — a job-level `if: github.event.issue.pull_request != null` condition skips the caller entirely when the labeled issue is not a PR. The `issues.labeled` event fires for both plain issues and PRs (since PRs are issues in GitHub's data model); this guard restricts the workflow to PRs only. No mutation occurs; non-PR issues that receive `agent:resolve-conflicts` simply do not trigger the workflow.
- **Label name predicate** — the trigger's `types: [labeled]` filter combined with a job-level `if: github.event.label.name == 'agent:resolve-conflicts'` ensures only the correct label fires the caller.

All pre-flight checks and mutations live in the reusable, executed in this order under the shared per-PR concurrency group:

1. **Fork check** (read-only, before authorization) — query `gh pr view $PR_NUMBER --json headRepository` and compare the head repository to the base repository. A null `headRepository` (returned when the PR's head fork has been deleted) is treated as fork-headed: the step skips with a `::notice::` and exits without mutating any labels, the same as a live fork PR. If the head repository is non-null and differs from the base repository, the step likewise skips with a `::notice::` and exits without mutating any labels. The `agent:resolve-conflicts` label stays on the PR (documenting the attempt) and no container is booted. This check is an API call rather than a pure `if:` expression because the `issues.labeled` event payload does not include the PR's head repository field (see Decision 6). Document the escape hatch in `AGENTS.md`: fork contributors can cherry-pick to a same-repo branch, same as the agent-review workaround.
2. **State gate** (read-only, before authorization) — if the PR is closed or merged, skip with a `::notice::` and exit. No label mutation at this step.
3. **Authorization** — the `check-agent-allowlist` gate job checks `sender-login` against `AGENT_ALLOWLIST`. Fails closed if the sender is not in the allowlist. All subsequent steps are gated on this job completing successfully.
4. **Clear `conflicts-escalated`** (post-authorization) — if the PR carries `conflicts-escalated`, remove it with a PR comment: "Operator re-attempted resolution via `agent:resolve-conflicts`; prior escalation marker removed." The entrypoint's existing `conflicts-escalated` preflight would otherwise abort the run before any attempt, and the operator applying the label is unambiguously expressing intent to re-attempt. Running this mutation after authorization ensures an unauthorized sender cannot clear the escalation marker by applying the label.
5. **Resolution** — pass `pr-number` to the existing matrix-of-one path.
6. **Label cleanup** — a final job removes `agent:resolve-conflicts` on success (mirroring the `agent:groom` lifecycle) and leaves it in place on failure so the operator can cycle the label to retry.

**Token and permission design for the label-trigger path.** The existing `agent-resolve-conflicts-reusable.yml` grants only `contents: read` and `pull-requests: read` — insufficient for the label mutations (steps 4 and 6) and PR comment (step 4) that the label-trigger path requires. This design requires permission changes at two levels, because a reusable workflow's top-level `permissions` block acts as a ceiling for all of its jobs — a caller cannot override a reusable-level downgrade — so the labeled caller's write grants alone are not enough to give `clear-escalation` and `cleanup` their required scopes.

**Caller-side grants** (`agent-resolve-conflicts-labeled.yml`): `contents: read` (required for the reusable's helper-ref API resolution and checkout steps — a called workflow cannot elevate its caller's token, so any scope omitted from the caller's `permissions:` block defaults to `none` and cannot be recovered inside the reusable), `issues: write` (required by the GitHub Labels API to remove `agent:resolve-conflicts` and `conflicts-escalated`), and `pull-requests: write` (required to post the step-4 audit comment via the PR comments API). The push-triggered caller (`agent-resolve-conflicts.yml`) retains only `contents: read` and `pull-requests: read` — no mutation occurs on the push path.

**Reusable-side job-level permissions** (`agent-resolve-conflicts-reusable.yml`): The reusable must not carry a top-level `permissions` block that restricts `issues: write` or `pull-requests: write`; instead, permissions are scoped at the job level so each job receives exactly what it needs and no more:
- `clear-escalation` (step 4) declares `permissions: { issues: write, pull-requests: write, contents: read }` — `issues: write` to remove `conflicts-escalated` via the Labels API; `pull-requests: write` to post the audit comment. When called from the push-triggered caller (which grants only `contents: read` and `pull-requests: read`), these scopes are capped by the caller's narrower grants; the job also does not run on the push path in any case (it is gated on `sender-login` being non-empty).
- `cleanup` (step 6) declares `permissions: { issues: write, contents: read }` — `issues: write` to remove `agent:resolve-conflicts` via the Labels API. The same push-path cap and gating applies.
- `resolve` (step 5, which boots the agent container) declares `permissions: { contents: read, pull-requests: read }`, keeping write-scoped `github.token` out of the job entirely. The agent container itself receives only the developer-agent App installation token minted via `./.github/actions/agent-token`, never `github.token`.

The workflow-contract tests must cover both sides of this split: (a) assert that the labeled caller declares all three grants (`contents: read`, `issues: write`, `pull-requests: write`), ensuring neither `contents: read` nor either write scope is inadvertently dropped; and (b) assert that the reusable's `clear-escalation` and `cleanup` jobs each carry the required job-level `permissions` blocks and that `resolve` retains only read-only job-level permissions — ensuring the per-job permission split is preserved and cannot be accidentally collapsed by a future top-level `permissions` block.

**Alternatives considered.**

- **Perform fork detection and `agent:resolve-conflicts` label removal in the caller before dispatching the reusable.** Rejected: the caller would mutate the PR (remove a label) before the reusable's allowlist gate has verified the sender. A label application from an unauthorized sender could thus cause a label mutation on the PR. Label mutations belong after authorization in the reusable; the fork check itself (a read-only API call) belongs in the reusable pre-flight because the `issues.labeled` event payload does not expose the head repository field (see Decision 6).
- **Perform `conflicts-escalated` removal and state guards in the caller before dispatching the reusable (original design).** Rejected per the established rule stated in Decision 3 and in `AGENTS.md § Repo-specific security defaults`: caller stubs may contain only queue predicates; reusable preflight gate jobs own lifecycle predicates and mutations. Moving mutations to the caller bypasses the authorization boundary: any label sender — including one not in `AGENT_ALLOWLIST` — could trigger PR-state changes (label removal, comment posting) before authorization.
- **Fail loudly on `conflicts-escalated` instead of auto-clearing it.** Rejected because the operator's action — applying `agent:resolve-conflicts` to an escalated PR — is itself the manual override signal. Requiring them to remove `conflicts-escalated` first would be a second manual step with no additional safety value; the PR comment documents what happened for audit.
- **Remove `agent:resolve-conflicts` from fork-headed PRs (to give the operator immediate feedback).** Not adopted for the same reason: the label removal is a mutation and cannot safely occur before authorization. The fork check pre-flight (step 1 in the reusable) exits before authorization, so the label stays on the fork PR rather than being removed — acceptable because (a) the sender has not yet been verified and (b) an authorized operator can manually remove the label from the PR conversation. The entrypoint's existing `conflicts-escalated` guard remains as defense-in-depth for the push-triggered path.
- **Keep the same-repo check as a pure `if:` expression in the caller (original design).** Not possible: the `issues.labeled` event payload does not include the PR's head repository field. Only `pull_request.labeled` carries `github.event.pull_request.head.repo.full_name` as a pure expression — but `pull_request.labeled` is suppressed for conflicted PRs (see Decision 6). The fork check therefore moves to the reusable as a read-only API call executed before authorization.

### Decision 5 — All-authors enumeration excludes fork PRs

**Decision.** When the `author-allowlist` input is non-empty (i.e., the resolver runs against more than the developer-agent's own PRs), the finder switches from the GitHub Search API to the REST Pulls API (`GET /repos/{owner}/{repo}/pulls?state=open&per_page=100`) for enumeration and applies two post-enumeration filters: (1) the **fork filter** — treats PRs where `head.repo` is `null` (the head fork was deleted after the PR was opened) as out of scope and skips them without throwing, then removes any remaining PRs where the head repository differs from the base repository (`head.repo.full_name != base.repo.full_name`); and (2) the **author filter** — when the allowlist is an explicit list of logins (not `["*"]`), retains only PRs whose `user.login` appears in `{<developer-author-bot-login>} ∪ {listed logins}`, where `<developer-author-bot-login>` is derived from the existing `author` input by stripping the `app/` prefix and appending `[bot]` (see Decision 1 bot-login normalization). Enumeration is bounded by two independent stops: a **50-page scan budget** (each page fetch counts against the shared 30-req/min guard) and a **100-candidate hard cap** on the in-scope (post-filter) set. When the page budget is exhausted before the candidate cap is reached, a `::warning::` annotation is emitted and pagination stops with the candidates collected so far; when the candidate cap is reached before the page budget is exhausted, the existing `::warning::` annotation fires and pagination stops. The combined filter, page budget, and candidate cap avoid wasting the full mergeability poll on PRs the resolver cannot push to or is not configured to touch, while ensuring the worst-case enumeration REST requests and runtime are bounded within the job timeout regardless of the in-scope filter ratio.

Implementation note: for the `["*"]` and explicit-list cases, the finder uses the REST Pulls API (`GET /repos/{owner}/{repo}/pulls?state=open&per_page=100`) for enumeration rather than the GitHub Search API. The Search API has a hard 1,000-result ceiling regardless of pagination strategy — paging until a short page cannot exceed that cap — so it cannot guarantee a complete sweep in repositories with more than 1,000 open PRs. The REST Pulls API does not have this ceiling; the finder paginates until an empty page is returned, subject to two hard stops: (a) a 50-page scan budget — once 50 pages have been fetched the finder emits a `::warning::` and stops with the candidates collected so far; and (b) the 100-candidate hard cap. Each page fetch counts as one request against the same 30-req/min guard used for the mergeability-poll phase: the guard is applied before each page fetch and before each polling-attempt wave, so enumeration and polling share a single rate-limit budget and a repository with a poor in-scope ratio (many fork PRs or non-allowlisted authors) cannot issue unchecked enumeration bursts that exceed the secondary rate limit or consume the job's wall-time budget before polling begins. Because the REST Pulls API returns the head repository field natively, no extra per-candidate API call is needed for fork detection during enumeration. The fork filter must be null-safe: `head.repo` is `null` for a PR whose fork was deleted after the PR was opened; reading `.full_name` on a null reference throws and would abort the entire sweep. The finder must check `head.repo == null` first and treat such PRs as out of scope (skipping them silently, as it would any other fork-headed PR), so a single stale deleted-fork PR cannot crash the enumeration loop. The post-query fork filter and author filter (for the explicit-list case) are applied before the hard cap is applied, so only in-scope (non-fork, allowlisted-author) candidates consume cap budget; the `::warning::` annotation is emitted and pagination stops only once 100 such candidates have been collected. Mergeability is polled with **bounded concurrency of P=5 candidates per batch** (not sequentially). The rate-limit guard uses **atomic batch reservation**: before each page fetch it waits until `requests_in_last_60s + 1 ≤ 30` and then increments the counter by 1; before each polling-attempt wave it waits until `requests_in_last_60s + batch.length ≤ 30` and then increments the counter by `batch.length`, so the full slot count for the wave is reserved before any parallel request is issued and no wave can burst past the 30-request limit — both phases share a single rolling 60-second request counter; the atomic batch reservation ensures correctness at phase transitions. The worst-case 60-second window spans the boundary between two consecutive back-to-back batches, capturing wave 5 of batch B-1 (at t+75s from B-1's start) and the first four waves of batch B (at t, t+5s, t+15s, t+35s), giving 5P = 5×5 = 25 requests in 60 seconds — safely within the 30-req/min limit. Because 5P=25 < 30, the guard never stalls the steady-state polling phase. With `DEFAULT_DELAYS` giving at most 75s per candidate across five attempts, the combined worst-case wall time is: enumeration (50 page fetches at ≤30-req/min ≈ 100s) + transition (≤10s, waiting for recent page fetches to age out of the 60s window before the first polling wave fires) + polling (`ceil(100/5) × 75s = 20 × 75s = 1,500s`) ≈ 1,610s (≈ 26.8 minutes) — within the `find-conflicted-prs` job's `timeout-minutes: 30`. The 30-req/min rate-limit guard applies before each page fetch and before each polling-attempt wave as a unified rate control with atomic batch reservation covering all REST requests in the job.

**Alternatives considered.**

- **Let the resolver fail per-PR when it can't push.** Rejected: that burns a token mint and a full container boot per fork PR on every push to `main`. The up-front filter keeps the finder's latency bounded.
- **Rely on branch protection alone to prevent the push.** Rejected because branch protection is on `main`, not on PR branches. The push failure would happen inside the container well after the resolver has already done the semantic work.

### Decision 6 — Separate caller stub for the label trigger

**Decision.** Add a new caller stub `.github/workflows/agent-resolve-conflicts-labeled.yml` with an `issues: types: [labeled]` trigger. Keep `.github/workflows/agent-resolve-conflicts.yml` as the push/dispatch caller. Both stubs call the same reusable workflow.

GitHub suppresses `pull_request` workflow runs entirely while a PR has merge conflicts — observed on PR #26 and documented in `docs/design/resolve-conflicts.md` § "Trigger: `push` to main, not PR events" and `docs/design/code-review-agent.md`. The `agent:resolve-conflicts` label is specifically designed to be applied to conflicted PRs; using `pull_request.labeled` as the trigger would therefore produce no workflow run in the exact case the feature addresses. GitHub's `issues.labeled` event is delivered for conflicted PRs (PRs are issues in GitHub's data model and the Issues API does not suppress events on merge conflicts), so `issues: types: [labeled]` is the trigger that fires reliably when the label is applied to a conflicted PR.

The key differences from a `pull_request.labeled` trigger: the `issues.labeled` event payload does not include the PR's head repository, so the same-repo fork check cannot be a pure `if:` expression in the caller (it moves to the reusable as a read-only API call — Decision 4, step 1). The PR number comes from `github.event.issue.number` and the sender from `github.event.sender.login`, both present in the `issues` event payload.

**Alternatives considered.**

- **Use `pull_request: types: [labeled]` as the trigger (original design).** Rejected: GitHub suppresses `pull_request` workflow runs for PRs with merge conflicts (parent design; PR #26). Applying the label to a conflicted PR therefore produces no workflow run, defeating the feature's purpose.
- **Add `issues: types: [labeled]` to the existing caller stub.** Rejected: the triggers (`push`, `workflow_dispatch`, `issues.labeled`) have incompatible permission needs and incompatible job-level `if:` conditions. Two stubs with narrow responsibilities are easier to review and to grep for ("who can trigger the resolver via label? find the file with `issues: labeled`").
- **Reuse `agent-auto-trigger.yml`.** Rejected: that workflow is designed to **apply** `agent:*` labels based on SDLC transitions, not to react to `agent:*` labels. Mixing the two roles in one workflow would overload its purpose.

### Decision 7 — Documentation lives at the sources, not duplicated

**Decision.** The new label is documented by its entry in `terraform/modules/labels/main.tf` (per `AGENTS.md § Volatile facts live at their sources`). The new variable is documented by its entry in `terraform/variables.tf`, `terraform/modules/agent-vars/main.tf`, and `terraform/modules/agent-vars/README.md`. `AGENTS.md` adds a one-paragraph entry for `agent:resolve-conflicts` in the Labels section (matching the shape of the `agent:review` entry), extends the MVP Workflow § 6 summary to mention the new setting and label trigger, and references this design doc. `README.md` gains the new Actions variable in its list of repo variables.

**Alternatives considered.**

- **Duplicate the label and variable definitions into `AGENTS.md` and `README.md`.** Rejected per the existing "Volatile facts live at their sources" rule. Only the operator-facing summary lines belong in the prose docs.

## Out of scope

- **Per-PR opt-out label for the extended sweep.** A label like `no-auto-resolve` that excludes a PR from the sweep is a reasonable refinement, but the initial design delegates per-PR exclusion to `conflicts-escalated`. Operators who want targeted coverage instead of broad coverage should use an explicit login list in `RESOLVE_CONFLICTS_AUTHOR_ALLOWLIST` rather than `["*"]`. Introducing a dedicated skip label can be a follow-up issue if operator feedback justifies it.
- **Auto-trigger of `agent:resolve-conflicts`.** The `AUTO_TRIGGER_AGENTS` family of knobs applies the `agent:<action>` label automatically on an SDLC transition. There is no obvious SDLC transition that should auto-apply `agent:resolve-conflicts` (the push-to-`main` reactive path already handles "a PR just became conflicted"), so the label is operator-applied only.
- **Branch-protection-signed-commits interaction.** If a PR branch has branch protection requiring signed commits and the developer-agent App does not sign, the resolver's push will be rejected. This is a pre-existing limitation of the resolver on any PR; the all-authors expansion inherits it. Document in the label's description and in `AGENTS.md` that the resolver can only succeed on branches the developer-agent App is allowed to push to.
- **Model overrides on the label-trigger path.** The push-triggered path already uses `vars.DEFAULT_MODEL` with no per-PR override; the label-triggered path inherits that. Future work can add a `model:*` PR-label resolver step (mirroring `agent-review`) if needed.
- **A workflow-dispatch operator-override on the label trigger.** The existing `workflow_dispatch` on `agent-resolve-conflicts.yml` already covers the "I want to run this resolver manually against one PR" use case for operators with workflow-dispatch access; the label trigger extends that capability to anyone in `AGENT_ALLOWLIST` (i.e., it does not require write access to Actions).
- **Updating `docs/design/resolve-conflicts.md`'s "Conflicts on human-authored PRs" out-of-scope line.** That is the parent design's record of the state at the time it was written; this new design supersedes that line by making it opt-in rather than forbidden. We do not edit the parent doc (merged design docs describe the accepted state at their merge time), but we cite the supersession here for traceability.
